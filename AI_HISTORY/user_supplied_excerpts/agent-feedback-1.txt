**这个任务本质上是：做一个“小型实时行情服务”，把一笔笔成交数据加工成一分钟 K 线，并证明它在异常情况下也有清楚、可信的行为。**

它**不是让你研究交易策略、预测涨跌，也不是做完整交易平台**。对你熟悉的量化系统来说，它就是其中的“行情接入 → 数据加工 → 提供给策略使用”这一层。

我的理解是：**计算 K 线只是题目的表层，真正考的是你能不能把一个看似简单的功能，做成别人敢依赖的工程组件。**

## 一、具体要做什么？

### 1. 输入：不断到来的成交记录

比如你的程序不断收到这些模拟成交：

| 成交时间 | 成交价格 | 成交数量 |
|---|---:|---:|
| 12:00:02 | 100 | 0.20 |
| 12:00:18 | 103 | 0.10 |
| 12:00:41 | 99 | 0.30 |
| 12:00:57 | 101 | 0.40 |

这些是**已经发生的成交**，不是挂单，也不是交易所已经计算好的 K 线。

### 2. 处理：把同一分钟的成交聚合起来

对于上面的模拟数据，`12:00:00–12:01:00` 这一分钟，你应当得到：

```text
Open：   100       第一笔成交的价格
High：   103       最高成交价格
Low：     99       最低成交价格
Close：  101       最后一笔成交的价格
Volume：1.00      成交数量之和
```

这就是常见的 OHLCV 数据。交易所的 K 线接口也会提供开、高、低、收、成交量等字段，但这道题要求你从成交数据自己构建，而不是直接转发交易所的结果。:chatgpt-content-reference{index="0"}

这里的“一分钟”应当理解成**固定的分钟区间**，而不是“每次取最近六十秒”。例如，我会约定使用 UTC 时间、左闭右开区间：

```text
12:00:00.000 ≤ 成交时间 < 12:01:00.000
```

恰好在 `12:01:00.000` 发生的成交，属于下一根 K 线。

### 3. 输出：让其他程序能使用这些 K 线

比如提供一个查询接口：

```http
GET /klines?symbol=BTCUSDT&limit=60
```

下游策略就可以读取最近六十根一分钟 K 线。

也可以选择实时推送或消息队列。**题目没有规定必须用哪种接口，也没有要求必须做网页图表。**重点是结果能被下游程序使用，而且使用方式、更新规则清楚。

## 二、哪些是必须做的，哪些由你决定？

这份题目给你的自由度很大，但有几项是明确要求。

| 内容 | 要求 |
|---|---|
| 一分钟 K 线服务 | 必须做，从流式成交数据构建 |
| 模拟数据供应器 | **必须做，即使已经接入 Binance 实时数据** |
| 测试和验证 | 必须提供，不能只有正常运行的演示 |
| 运行与设计说明 | 说明如何运行、如何评估、采用什么假设、为什么这样设计 |
| AI 聊天记录 | 必须提交相关工具和会话的记录，允许脱敏 |
| Binance 实时接入 | 可选，使用实时数据本身没有评分优势 |
| Redis、数据库、框架、语言 | 自己选择，没有指定技术加分 |
| 全部生产级功能 | 不要求一天内全部完成，但必须诚实说明边界 |

还有两个容易忽略的条件：

**第一，允许 AI，不允许找其他人帮忙。**你可以用 ChatGPT、Codex、Claude Code 做调查、实现、测试和审查，但不能让朋友、同事替你设计或调试。

**第二，允许提交未完成的版本。**他们明确要求区分“已实现并验证”“已实现但未验证”“尚未实现”，而不是要求你包装出一个看起来无所不能的系统。

所以，它不是一道“猜面试官想让你用什么技术”的题，而是一道**要求你自己划定范围、定义行为、证明结果的开放工程题**。

## 三、真正的难点：不是怎么算，而是哪些数据可以相信

只按正常数据计算，逻辑确实很短。但这份题目明确要求考虑现实条件，我认为下面这些问题才是重点。

### 1. 按成交时间分桶，还是按收到消息的时间分桶？

假设一笔成交：

```text
实际成交时间：12:00:59.900
程序收到时间：12:01:00.200
```

它应该进入 `12:00` 那根 K 线，而不是 `12:01`。

这就是**事件发生时间和程序处理时间的区别**。流处理系统还需要面对事件延迟到达、到达顺序不一致等问题。:chatgpt-content-reference{index="1"}

如果接 Binance 现货成交数据，其消息中的 `T` 是成交时间，`E` 是事件时间；我会明确选择 `T` 来划分分钟，另外记录本地接收时间用于观察延迟。:chatgpt-content-reference{index="2"}

这类选择应当写进设计说明，不能只是代码里碰巧用了某个字段。

### 2. 成交乱序到达，开盘价和收盘价会不会算错？

考虑这个例子：

```text
先收到：12:00:50，价格 105
后收到：12:00:10，价格 100
```

如果代码写成：

```text
每收到一笔成交，就把 Close 更新为这笔价格。
```

最终收盘价就会错误地变成 `100`。

**开盘价和收盘价应当依据成交的先后关系，而不是消息抵达程序的顺序。**

我的建议是，为这个项目规定一个确定的排序规则，例如按照：

```text
成交时间 → 同时间情况下的成交 ID
```

来选择首笔和末笔，并说明第二项是本项目的数据源约定，不能默认所有供应商的 ID 都有相同语义。

这也让测试更明确：**在允许的迟到范围内，同一组成交换一种到达顺序，最终结果不应改变。**

### 3. 同一笔成交收到两次，成交量会不会翻倍？

例如：

```text
第一次收到 trade_id=123，数量 0.5
随后又收到 trade_id=123，数量 0.5
```

如果没有去重，成交量就会被计算成 `1.0`。

我会要求每笔标准化成交有明确的身份标识，并以类似：

```text
数据源 + 市场 + 交易对 + 成交 ID
```

作为去重依据，避免不同交易对恰好使用相同 ID 时发生误判。

但这里还有第二层问题：**去重记录保存多久？**

不能为了去重，让内存中的 ID 集合无限增长。因此需要把去重保留范围、允许迟到范围、历史重放规则一起定义，而不是简单加一个永不清理的集合。

### 4. 到了下一分钟，上一根 K 线真的已经“最终确定”了吗？

不一定。

例如，到 `12:01:00` 时，你准备输出上一分钟的 K 线，但某笔属于上一分钟的成交还在路上。

你必须选择一种政策：

**可以等待一个有限的宽限期；可以允许后续修订；也可以截止后不再修改，但明确记录被拒绝的迟到成交。**

流处理中的水位线、触发器等机制，就是用来处理结果何时输出、怎样接受迟到数据，以及完整性和延迟之间的取舍。它们并不是“所有数据一定已经到齐”的魔法保证。:chatgpt-content-reference{index="3"}

对这个作业，我倾向于采用容易解释和测试的方案：

> 分钟结束后保留一个可配置的宽限期；期间允许更新，之后封口。超期成交不静默改变已封口的数值，而是记录并暴露数据质量风险。

这里还需要考虑两个细节：没有下一笔成交时，仍应通过定时器或模拟时钟推进封口；封口时不能忽略已经接收、但尚未处理的积压。

**尤其重要的是：“不再更新”和“数据完整”不是一回事。**

我会把它们拆成两个维度，例如：

```text
is_final：这根 K 线的数值是否还会更新
data_quality：是否存在已知缺口，或完整性无法确认
```

### 5. “没有成交”和“没有收到成交”不能混为一谈

假设一分钟没有收到任何消息，至少可能有两种情况：

```text
情况 A：这一分钟确实没有成交。
情况 B：连接断了，所以你没有收到成交。
```

仅凭“没有消息”，不能区分这两者。

对于能够确认的无成交区间，可以选择不生成 K 线，也可以明确生成“沿用上一收盘价、成交量为零”的合成 K 线。但这是你要声明的产品规则。

**对于断流区间，不能把缺失数据直接包装成零成交量。**

还有一个特别值得做的测试：

> 程序在 `12:00:30` 启动，第一根 `12:00` K 线应该怎样标记？

没有历史补数，就没有这一分钟前三十秒的成交。它不能被无说明地当作完整一分钟的数据。

同样，**断线重连成功，只说明连接恢复，不说明断线期间的数据已经补齐。**一天内不做自动补数完全可以，但应把受影响区间标出来。

### 6. 价格和数量的精度怎么处理？

我会避免直接用普通二进制浮点数累计价格和数量，而是选择从原始字符串构造 `Decimal`，并为本项目的数据范围配置足够的计算精度。Python 官方文档明确说明，十进制数可由 `Decimal` 精确表示，而许多十进制小数无法由二进制浮点数精确表示。:chatgpt-content-reference{index="4"}

此外，我会定义：成交量是基础资产数量；成交额是价格乘数量之和。不要把这两个字段混在一起。

缺少字段、非法数字、负数量、异常未来时间戳等输入，也需要明确的拒绝和记录规则。

## 四、如果是我做，一天内会采用什么方案？

**我会选择“小而完整的闭环”，而不是先搭大型架构。**

我的初版范围会是：一个市场、一种周期、少量交易对、单进程运行，以模拟源作为主要验收入口。

整体结构可以是：

```text
模拟成交源 / 可选 Binance 成交源
              ↓
         统一 Trade 数据格式
              ↓
          校验、去重
              ↓
         一分钟 K 线聚合
              ↓
       近期结果存储、质量状态
              ↓
           查询接口
```

### 核心聚合器必须和网络、数据库分开

这是我最看重的结构选择之一。

聚合器负责接收标准化成交、维护窗口状态、按约定输出结果；它不应该直接负责连接 Binance、解析网络错误或处理 HTTP 请求。

这样，无论数据来自模拟器、实时连接，还是以后增加的历史重放，**都可以走同一套聚合逻辑**。

如果接 Binance，我会先限定为现货，优先使用 `@trade` 原始成交流。`@aggTrade` 是聚合成交，使用它并非一定错误，但不能把一条聚合消息不加说明地当作一笔原始成交。:chatgpt-content-reference{index="5"}

### 并发方面，我会先让一个聚合任务拥有状态

网络接收可以异步进行，但成交更新和窗口封口，尽量由同一个聚合循环执行，避免多个任务同时修改同一根 K 线。

输入队列设置容量上限。Python 的 `asyncio.Queue` 在配置正数 `maxsize` 后，队列满时 `put()` 会等待，这可以作为基本的背压机制。:chatgpt-content-reference{index="6"}

但我不会因此宣称“不会丢数据”：持续过载仍可能造成延迟或上游断开。因此还要观察队列积压，并在无法保持输入完整时暴露问题。

初版也应明确只启动一个行情处理实例；不能随手把服务配置成多个独立 worker，却没有解决重复订阅和状态归属。

### 对外接口先做一种，不必全部做

我会先提供清楚的 HTTP 查询接口，包含当前未封口 K 线、近期历史和质量状态。实时推送可以在核心验证完成之后再加。

存储也可以先保留有限的内存历史，时间允许再增加 SQLite 持久化。但必须说明：

> 保存已完成的 K 线，不等于已经实现未完成窗口的崩溃恢复。

如果重启后没有恢复原始成交、去重状态和未完成窗口，就应该按这个限制处理，而不是宣称“支持无损恢复”。

### Redis 要不要用？

**不是必需，取决于你要解决什么问题。**

如果只是单服务生成结果、下游主动查询，我认为可以先不引入 Redis。

如果要让独立消费者断线后继续读取输出，Redis Streams 值得考虑；但普通 Redis Pub/Sub 是至多一次投递，订阅者断线时错过的消息不会自动重放，不能拿它当作可靠补读机制。:chatgpt-content-reference{index="7"}

所以，我不会为了题目提到 Redis 就使用它。**引入组件要能回答：它解决了哪个已明确的问题，代价是什么？**

## 五、模拟器和测试怎么做，才真正有说服力？

我认为，**模拟器很可能是这个作业最值得投入的部分之一**。因为题目明确不奖励实时接入本身，而模拟器能证明你主动识别了哪些失败情形。

### 模拟器应当能“编排事件”，不只是随机生成价格

比如同一笔成交可以分别定义：

```text
成交发生时间：12:00:59.900
模拟到达时间：12:01:00.200
```

这样才可以模拟跨分钟延迟、乱序、重复、断流和重连。

我会让它支持固定场景和固定随机种子，并使用可控制的模拟时钟。测试一分钟窗口，不应每次都真的等待一分钟。

值得覆盖的场景包括：

| 场景 | 验证重点 |
|---|---|
| 正常成交、跨分钟边界 | OHLCV 和窗口归属正确 |
| 允许范围内的乱序 | 开、收取决于成交顺序，而不是到达顺序 |
| 重复成交 | 成交量和笔数不增加 |
| 相同时间戳的多笔成交 | 首末成交选择稳定、可解释 |
| 超过宽限期才到达 | 严格遵守已声明的迟到政策 |
| 无成交、断流、半分钟启动 | 不伪装成完整行情 |
| 多交易对交错输入 | 状态和去重不互相污染 |
| 突发流量、非法消息 | 有明确的积压、拒绝和错误行为 |

这些不一定都需要复杂实现。例如，不支持自动补数时，测试“断流后正确标记不完整”，同样是有意义的验证。

### 我会特别加入一套独立的参考计算

这是题目中 “independent checks” 很值得认真回应的地方。

比如把一组已知成交用另一种简单方法离线计算：

```text
先去重 → 按约定排序 → 按分钟分组 → 直接计算 OHLCV
```

然后与流式聚合器的结果比较。

**参考计算不要直接复用生产聚合器的关键逻辑。**否则两个结果可能只是一起犯了同一个错误。

同时，比较要遵守同一份输入契约：在全部成交都被允许接纳的场景，比较完整结果；在故意制造超期迟到的场景，按既定接纳规则检查，而不是要求流式结果包含已经明确拒收的数据。

### 再做一次完整链路验证

不仅单测聚合函数，还要验证：

> 启动服务 → 模拟器送入场景 → 从对外接口读取 → 对照预期结果。

这样才能证明你提交的是一个能被使用的服务，而不只是一个计算正确的函数。

## 六、他们为什么要求交 AI 聊天记录？

从题目的评估标准看，他们不仅想知道“AI 有没有写代码”，还想看：

**你能不能有效分配任务、检查输出、发现错误，并让工程工作可以继续。**

我会把 AI 用在四个环节：调查接口和语义、实现受限模块、设计反例测试、审查代码和文档的一致性。

但决定采用什么行为、测试是否充分、哪些结论可以相信，仍然由你负责。

例如，值得保留的真实工程记录可能是：

> 最初实现按照消息到达顺序更新 Close；后来用乱序案例发现问题；修改首末成交判断；增加回归测试。

这比一份只有“请写代码”“已完成全部功能”的聊天记录，更能呈现你对结果的判断。

**这类记录必须是真实发生的，不要事后编造。**从当前这次讨论开始，就可以保存相关技术交流；提交时保留失败、修正和验证过程，删除凭证、密钥及不相关的私人内容。

项目中也应注明重要复用组件及来源。运行说明则要让面试官能够复现，而不是只写“本人机器运行正常”。

## 七、我对这道题的总体判断

### 它更偏工程判断，不是复杂算法

从题面看，考点不在高级数学、预测能力或者极限低延迟优化，而在于：

> 一个持续接收外部数据的系统，如何定义正确性、维护状态、处理失败，以及告诉消费者哪些结果可信。

所以，最值得花精力的不是先把系统做大，而是把**时间、顺序、重复、最终性和完整性**这几个概念定义清楚。

### 我会按“可验证程度”安排优先级

先完成模拟源、聚合器、基本接口和有预期结果的测试；再补上迟到、去重、断流和启动边界；最后根据剩余时间加入实时接入、持久化、订阅或自动补数。

不是说后面的功能不重要，而是**一个实现清楚、验证充分、限制诚实的版本，比一个功能很多但无法解释正确性的版本更符合这份题目。**

### 对你而言，最应该展示的是“行情可信度意识”

你已经做过量化平台，这道题可以把关注点从“能接行情、能生成 K 线”，推进到：

**“我能解释每根 K 线由哪些成交构成，为什么是这个结果，什么时候还会变化，以及什么时候下游不应该相信它。”**

我认为，这就是这份作业最核心的价值：**不是证明你能画出一根 K 线，而是证明你知道怎样让策略安全、明确地使用这根 K 线。**
